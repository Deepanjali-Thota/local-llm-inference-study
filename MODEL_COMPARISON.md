# Model Comparison

Hardware: Intel i5-1335U, 16 GB RAM, CPU only. All models Q4_K_M, temperature 0.
Task: support ticket classification. Tuning set: 40 manually labeled tickets (10 per category, 9 hard). Held-out sets: 16 tickets (Run 3) and 48 policy-labeled tickets (Run 5).

## Run 1: category names only in prompt

| Model | Params | Accuracy | Hard acc. | Valid | Latency (s) | Gen tok/s | RAM (GB) |
|---|---|---|---|---|---|---|---|
| llama3.2:3b | 3.2B | 80% | 78% | 100% | 2.28 | 13.9 | 4.1 |
| phi4-mini | 3.8B | 80% | 78% | 92% | 2.82 | 11.7 | 4.8 |
| mistral:7b | 7.2B | 88% | 56% | 85% | 6.43 | 6.4 | 6.8 |

## Run 2: category definitions added to prompt

| Model | Params | Accuracy | Hard acc. | Valid | Latency (s) | Gen tok/s | RAM (GB) |
|---|---|---|---|---|---|---|---|
| llama3.2:3b | 3.2B | 95% | 89% | 100% | 2.32 | 13.8 | 4.1 |
| phi4-mini | 3.8B | 98% | 100% | 95% | 3.07 | 11.7 | 4.8 |
| mistral:7b | 7.2B | 95% | 89% | 80% | 6.56 | 5.9 | 6.8 |

## Findings
- Category definitions improved accuracy by +15 to +18 points for the small models. Moving from 3B to 7B gave only +8 in Run 1. Prompt design mattered more than model size.
- In Run 1, llama3.2:3b and phi4-mini made the same errors (receipt, student discount, and most "other" tickets → account). Shared errors across models pointed to the prompt, not the model.
- In Run 1, mistral:7b was 97% accurate on easy tickets but worst on hard ones (5/9); its errors were mostly defensible (feature requests → technical).
- mistral:7b had the lowest valid rate (80–85%): it wrote summaries over 6 words most often, which would trigger retries in production.
- mistral:7b is ~2.8x slower and uses ~65% more RAM than llama3.2:3b, with no accuracy gain after the prompt fix.

## Limitations
- 40 tickets: a 1-ticket difference is 2.5 points, so 95% vs 98% is not a meaningful gap. Hard accuracy uses only 9 tickets.
- Definitions were written after seeing Run 1 errors on the same tickets, so Run 2 may overfit. Tested in Runs 3 and 5: with policy-consistent labels (Run 5), accuracy stayed at 90–94%.
- Labels are one person's judgment; hard tickets are genuinely ambiguous.
- Run 1 per-ticket CSV was reconstructed from the console log (no per-ticket gen tok/s; latency rounded to 0.1s).

## Run 3: Held-out test (16 new tickets, generated by a different model, labels reviewed)

| Model | Accuracy | Hard acc. | Valid | Latency (s) | Gen tok/s | RAM (GB) |
|---|---|---|---|---|---|---|
| llama3.2:3b | 69% | 25% | 100% | 2.39 | 14.6 | 4.1 |
| phi4-mini | 88% | 50% | 81% | 3.41 | 11.6 | 4.8 |
| mistral:7b | 88% | 75% | 56% | 7.60 | 5.9 | 6.8 |

### Error analysis
- Accuracy dropped on unseen tickets (llama 95% → 69%). *Revised in Run 5: most of this drop came from labeling-policy mismatch, not overfitting.*
- 3 of the 5 failing tickets (#8, #15, #16) are label-policy conflicts, not clear model errors: the held-out labels came from a different labeler whose rules differ from the prompt's definitions (e.g. the prompt defines permissions as `account`, the label said `technical`). Labels were kept as-is to avoid tuning the answer key after seeing results.
- llama3.2:3b made the only clear error (#3: "switch to monthly billing" → account) and sent all 5 errors to `account`, suggesting it classifies on surface words ("account", "workspace", "admin", "permission").
- All phi4-mini and mistral:7b errors were on contested labels; both generalized better than llama.
- mistral:7b passed the summary rule only 56% of the time; in production about half its answers would need a retry.

### Lesson
A held-out set must use the same labeling policy as the system it tests. Write the policy first, then label against it.

## Run 4: Quantization (llama3.2:3b, Q4_K_M vs Q5_K_M vs Q8_0)

| Quant | Size on disk | Accuracy (40) | Accuracy (held-out 16) | Median latency (40) | Gen tok/s | RAM (GB) |
|---|---|---|---|---|---|---|
| Q4_K_M | 2.0 GB | 95% | 69% | 2.26s | 14.1 | 4.1 |
| Q5_K_M | ~2.3 GB | 92.5% | 69% | 2.76s | 12.6 | 4.4 |
| Q8_0 | ~3.4 GB | 95% | 69% | 3.66s | 9.1 | 5.5 |

### Findings
- All three quantization levels made the same errors (#6 and #10 on the original set; the same 5 held-out tickets). Q5 missed one extra ticket, within noise. Errors come from what the model learned, not from weight rounding.
- Generation speed scaled with model size: Q8 is ~1.7x larger and ~1.6x slower (14.1 → 9.1 tok/s), consistent with generation being memory-bandwidth bound on CPU.
- Decision: Q4_K_M. Higher precision added latency and RAM with no accuracy gain on this task.

### phi4-mini: Q4_K_M vs Q8_0 (held-out 16 tickets, same run)

| Quant | Accuracy | Valid | Median latency | Gen tok/s | RAM (GB) |
|---|---|---|---|---|---|
| Q4_K_M | 88% | 81% | 2.72s | 14.0 | 4.8 |
| Q8_0 | 88% | 81% | 4.86s | 9.0 | 6.4 |

- Q8 produced identical classifications to Q4 on every ticket (same 2 errors, same 3 invalid summaries), while running 1.8x slower and using 1.6 GB more RAM.
- Same result as llama3.2:3b across two model families: for this task, Q4_K_M is the right trade-off.
- Note: phi4-mini Q4 latency varied between sessions (3.41s vs 2.72s) due to laptop load; comparisons are made within a single run.

## Run 5: Policy-consistent held-out set (48 tickets)

Labels written against `LABEL_POLICY.md` (generated by a different model, checked against the policy, near-duplicates of the tuning set removed). Accuracy with 95% Wilson confidence intervals.

| Model | Accuracy | 95% CI | Hard acc. | Valid |
|---|---|---|---|---|
| llama3.2:3b | 90% (43/48) | 78–95% | 83% | 100% |
| phi4-mini | 94% (45/48) | 83–98% | 83% | 92% |
| mistral:7b | 90% (43/48) | 78–95% | 83% | 62% |

### Findings
- With labels that follow the same policy as the prompt, llama3.2:3b scored 90%, vs 69% on the first held-out set. Most of that earlier drop came from labeling-policy mismatch, not overfitting.
- Confidence intervals overlap heavily; no model is significantly more accurate on this data.
- 7 of 13 errors were billing tickets about plan, seat or discount changes, and 3 were permission tickets labeled `technical`. Both match tie-break rules in the policy that are not in the prompt. Errors cluster where the policy and prompt differ.
- mistral:7b passed the summary rule only 62% of the time, consistent with earlier runs.
- The laptop slept during the phi4-mini run (two tickets took 2307s and 5113s). Median latency was unaffected, but speed numbers from this run are not used.

### Future work
- Add the tie-break rules to the prompt, then evaluate on a new, unseen set.
